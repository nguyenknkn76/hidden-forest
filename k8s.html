💡 So sánh nhanh: Docker Compose vs Kubernetes

Docker Compose (Quản lý nhà trọ): Bạn có 1 file excel (`docker-compose.yaml`) ghi rõ phòng nào cần gì. Bạn phải tự mình setup. Nếu phòng cháy, nó sập luôn và bạn phải tự đi sửa.
Kubernetes (Chuỗi khách sạn 5 sao): Bạn là CEO, chỉ ra lệnh: "Tôi muốn *luôn luôn có* 3 phòng 'backend' sẵn sàng". Hệ thống (K8s) sẽ tự tìm khách sạn (Node) trống, setup phòng (Pod), treo biển chỉ dẫn (Service), và quan trọng nhất: nếu phòng (Pod) cháy, hệ thống *tự động* xây lại phòng y hệt ở chỗ khác.

Trước khi bắt đầu, chúng ta cần một "sân chơi". Các hướng dẫn này được tối ưu cho Fedora 42.

1. Cài đặt Docker

Docker là nền tảng. K8s điều phối containers, nên bạn cần Docker để build và chạy chúng.

# Khởi động và cho phép Docker chạy cùng hệ thống

3. Cài đặt Local Cluster (Chọn 1)

Lựa chọn A: Minikube (Khuyên dùng)

Minikube giả lập một cluster K8s (thường là 1 node) bên trong máy ảo hoặc container. Rất tốt để học.

# Cài đặt Minikube (tải binary)
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube

# Khởi động cluster Minikube (dùng driver docker)
minikube start --driver=docker

Lựa chọn B: Kind (Kubernetes in Docker)

Kind chạy mỗi *node* K8s như một container. Tốt cho việc thử nghiệm multi-node.

# Cài đặt Kind (tải binary)
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind

# Tạo cluster
kind create cluster --name dev-cluster

🧠 Khái niệm Cốt lõi

Đây là những "building blocks" của Kubernetes. Hiểu rõ chúng là chìa khóa để làm chủ K8s. Hãy chọn một chủ đề bên dưới để khám phá.

Pod, ReplicaSet, và Deployment

Đây là bộ ba cốt lõi để chạy ứng dụng stateless của bạn.

  • Pod (Bóng đèn): Đơn vị chạy nhỏ nhất, bọc quanh container. Nếu bóng đèn (Pod) cháy, nó sẽ tắt ngóm.
  • ReplicaSet (Công tắc đảm bảo): Bạn nói: "Tôi muốn 3 bóng đèn luôn sáng". Nếu 1 bóng cháy, ReplicaSet sẽ tự động lắp bóng mới.
  • Deployment (Hệ thống nhà thông minh): Bạn nói: "Hãy đổi 3 bóng đèn v1 sang v2". Deployment sẽ quản lý ReplicaSet, từ từ tắt bóng v1 và bật bóng v2 (Rolling Update).

→ Bạn sẽ luôn làm việc với `Deployment`.

Ví dụ: Deployment cho Nginx

File `my-backend-dep.yaml` này yêu cầu K8s chạy 3 bản sao (replicas) của image `nginx`.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-backend-api
spec:
  replicas: 3 # Chúng ta muốn 3 Pod
  selector:
    matchLabels:
      app: my-backend # Deployment này quản lý Pod nào có label này
  template: # Đây là "khuôn mẫu" (template) của Pod
    metadata:
      labels:
        app: my-backend # Pod này được gán label 'my-backend'
    spec:
      containers:
      - name: backend-container
        image: nginx:1.25
        ports:
        - containerPort: 80

# Áp dụng file
kubectl apply -f my-backend-dep.yaml

# Xem 3 Pods đang chạy
kubectl get pods

# Thử "giết" 1 Pod (K8s sẽ tự tạo lại ngay)
kubectl delete pod

Service và Ingress

Bạn đã có Pod, nhưng làm sao để giao tiếp với chúng?

  • Service (Tổng đài nội bộ): Cung cấp 1 IP *ổn định* (ClusterIP) bên trong cluster. Khi `frontend` gọi "backend-service", tổng đài (Kube-Proxy) sẽ kết nối nó đến 1 trong 3 Pod `backend` đang rảnh. (Layer 4 - TCP/UDP).
  • Ingress (Bảo vệ cổng chính): Là bộ quy tắc cho traffic từ *bên ngoài* (Internet) đi vào. Nó xem xét tên miền, đường dẫn (`/api`) để quyết định "đường này đi tới Service A", "đường kia đi tới Service B". (Layer 7 - HTTP/HTTPS).

Ví dụ: Expose Deployment bằng Service (NodePort)

File `my-backend-svc.yaml` này tạo 1 Service để truy cập các Pod có label `app: my-backend`.

apiVersion: v1
kind: Service
metadata:
  name: my-backend-service
spec:
  type: NodePort # Dùng NodePort để test trên Minikube
  selector:
    app: my-backend # Phải khớp với 'labels' của Pod
  ports:
  - protocol: TCP
    port: 80 # Port của Service
    targetPort: 80 # Port trên Pod

# Áp dụng file
kubectl apply -f my-backend-svc.yaml

# Lấy URL để test (chỉ dành cho Minikube)
minikube service my-backend-service

Ví dụ: Định tuyến bằng Ingress

File `my-ingress.yaml` này định nghĩa quy tắc: `/api` đi đến `backend-service`, `/` đi đến `frontend-service`.

# (Chỉ làm 1 lần) Bật Ingress Controller trên Minikube
minikube addons enable ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
spec:
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: my-backend-service # Chuyển đến Service backend
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: my-frontend-service # Chuyển đến Service frontend
            port:
              number: 80

ConfigMap và Secret

Cách để tách cấu hình (config) ra khỏi code (image).

  • ConfigMap (Bảng tin công cộng): Lưu trữ cấu hình *không nhạy cảm* dạng key-value (ví dụ: `LOG_LEVEL=debug`).
  • Secret (Két sắt): Lưu trữ thông tin *nhạy cảm* (ví dụ: `DB_PASSWORD=123`). Dữ liệu được encode base64 (chỉ để che mắt, không phải mã hóa).

Ví dụ: Inject ENV vào Deployment

1. Tạo ConfigMap và Secret bằng CLI:

# Tạo ConfigMap (lưu DB host và user)
kubectl create configmap my-backend-config \
  --from-literal=DB_HOST=postgres-service \
  --from-literal=DB_USER=admin

# Tạo Secret (lưu password)
kubectl create secret generic my-backend-secret \
  --from-literal=DB_PASSWORD=admin123

2. Cập nhật `my-backend-dep.yaml` để sử dụng chúng:

... (apiVersion, kind, metadata, spec, replicas, selector, template, metadata) ...
        spec:
          containers:
          - name: backend-container
            image: my-company/my-backend:v1.2
            ports:
            - containerPort: 8080
            env: # === PHẦN QUAN TRỌNG ===
              # Lấy giá trị từ ConfigMap
              - name: DATABASE_HOST
                valueFrom:
                  configMapKeyRef:
                    name: my-backend-config # Tên ConfigMap
                    key: DB_HOST # Key bên trong
              # Lấy giá trị từ Secret
              - name: DATABASE_PASSWORD
                valueFrom:
                  secretKeyRef:
                    name: my-backend-secret # Tên Secret
                    key: DB_PASSWORD # Key bên trong

Volume, PersistentVolume (PV) và PVC

Làm thế nào để lưu trữ dữ liệu cho Database (ứng dụng stateful)?

Quy trình Yêu cầu Kho:

  1. Admin (PV - Kho): Chuẩn bị sẵn các ổ cứng (PersistentVolume) và cất vào kho.
  2. Dev (PVC - Phiếu yêu cầu): Gửi một phiếu (PersistentVolumeClaim) nói: "Tôi cần 1GB ổ cứng".
  3. K8s (Hệ thống): Tìm trong kho 1 PV phù hợp và *gắn* (bind) nó với PVC.
  4. Dev (Pod): Tạo Pod (ví dụ: Postgres) và nói: "Hãy dùng ổ cứng được gán cho phiếu PVC này".

→ Nếu Pod chết và khởi động lại ở Node khác, nó sẽ tự động được gắn lại đúng ổ cứng đó (vì ổ cứng gắn với PVC, không phải Pod). Dữ liệu an toàn!

Ví dụ: Chạy Postgres với Data bền vững

1. Tạo `postgres-pvc.yaml` (Phiếu yêu cầu):

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-db-pvc
spec:
  accessModes:
    - ReadWriteOnce # Chỉ 1 Pod được đọc/ghi (chuẩn cho DB)
  resources:
    requests:
      storage: 1Gi # Tôi cần 1GB

2. Tạo `postgres-dep.yaml` (Dùng phiếu yêu cầu):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres-db
spec:
  replicas: 1
  ... (selector, template) ...
        spec:
          containers:
          - name: postgres
            image: postgres:15
            env: 
              - name: POSTGRES_PASSWORD
                value: "admin123" # (Nên dùng Secret ở đây!)
            volumeMounts: # === PHẦN 1 ===
              - name: postgres-storage # Tên (nội bộ)
                mountPath: /var/lib/postgresql/data # Mount vào thư mục data
          volumes: # === PHẦN 2 ===
            - name: postgres-storage # Tên này phải khớp 'volumeMounts.name'
              persistentVolumeClaim:
                claimName: postgres-db-pvc # Trỏ đến "phiếu yêu cầu" (PVC)

🔄 So sánh nhanh

Các bảng so sánh này giúp bạn phân biệt rõ ràng các khái niệm dễ nhầm lẫn, tất cả ở cùng một nơi.

Pod vs ReplicaSet vs Deployment

Tính năng Pod ReplicaSet (RS) Deployment (Deploy)
Mục đích Đơn vị chạy (bọc container) Đảm bảo số lượng (replicas) Quản lý vòng đời, cập nhật (versioning)
Tự phục hồi? Không. Nếu chết là chết. Có. Tạo Pod mới nếu thiếu. Có (thông qua RS).
Cập nhật? Không Không (phải tạo RS mới) Có (Rolling Update)
Khi nào dùng? Không bao giờ tạo trực tiếp (trừ khi debug). Không bao giờ tạo trực tiếp. Luôn luôn dùng cái này.

Service vs Ingress

Tính năng Service (svc) Ingress
Mục đích Kết nối nội bộ (service-to-service) và cân bằng tải. Kết nối bên ngoài (user-to-service) và định tuyến HTTP.
Layer (OSI) Layer 4 (TCP/UDP). (Không hiểu HTTP) Layer 7 (HTTP/HTTPS). (Hiểu paths, domains)
Giống đời thực Tổng đài nội bộ. Gọi "Lễ tân" (tên Service), nó tự kết nối 1 trong 3 lễ tân (Pods). Bảo vệ cổng chính. Quyết định `domain/api` -> Tòa nhà Backend.
Khi nào dùng? Luôn luôn. (Backend gọi DB, Frontend gọi Backend). Khi cần expose app ra Internet qua tên miền.

ConfigMap vs Secret

Tính năng ConfigMap Secret
Mục đích Cấu hình không nhạy cảm Cấu hình nhạy cảm
Lưu trữ Plain text (văn bản thuần túy) Base64 encoded (chỉ che mắt, không mã hóa)
Ví dụ `DB_HOST=postgres.default.svc` `DB_PASSWORD=...` `JWT_SECRET=...`

🚀 Thực hành: Chuyển Docker Compose sang K8s

Đây là mục tiêu chính của bạn. Chúng ta sẽ chuyển đổi file `docker-compose.yaml` (bên trái) thành một bộ 7 file manifest của Kubernetes (bên phải). Hãy nhấp qua lại giữa các tab để so sánh, và nhấp vào các file YAML bên tab Kubernetes để xem chi tiết.

File Nguồn: `docker-compose.yaml`

version: '3.8'
services:
  backend-api:
    image: my-company/backend:v1.5
    build: ./backend
    ports:
      - "8000:8000"

      - DB_HOST=postgres-db
      - DB_USER=admin
      - DB_PASS=supersecret
      - REDIS_HOST=redis-cache
    depends_on:
      - postgres-db
      - redis-cache

  frontend-web:
    image: my-company/frontend:v1.1
    build: ./frontend
    ports:
      - "80:80"
    environment:
      - API_URL=http://localhost:8000/api

  postgres-db:
    image: postgres:15
    environment:
      - POSTGRES_USER=admin
      - POSTGRES_PASSWORD=supersecret
    volumes:
      - postgres_data:/var/lib/postgresql/data

  redis-cache:
    image: redis:7
    
volumes:
  postgres_data:

File Đích: Kubernetes Manifests

01-db-pvc-secret.yaml

Mã hóa `POSTGRES_USER` và `POSTGRES_PASSWORD` vào Secret. Yêu cầu (Claim) 2GB lưu trữ cho DB.

apiVersion: v1
kind: Secret
metadata:
  name: postgres-secret
type: Opaque
data:
  # echo -n 'admin' | base64 -> YWRtaW4=
  # echo -n 'supersecret' | base64 -> c3VwZXJzZWNyZXQ=
  POSTGRES_USER: YWRtaW4=
  POSTGRES_PASSWORD: c3VwZXJzZWNyZXQ=
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi

02-db-deployment-service.yaml

Tạo Service `postgres-service` (để backend gọi) và Deployment cho Postgres, sử dụng Secret và PVC đã tạo.

apiVersion: v1
kind: Service
metadata:
  name: postgres-service
spec:
  type: ClusterIP
  selector: {app: postgres}
  ports:
  - port: 5432
    targetPort: 5432
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: postgres-db
spec:
  replicas: 1
  selector:
    matchLabels: {app: postgres}
  template:
    metadata:
      labels: {app: postgres}
    spec:
      containers:
      - name: postgres
        image: postgres:15
        envFrom:
          - secretRef:
              name: postgres-secret
        volumeMounts:
        - name: postgres-storage
          mountPath: /var/lib/postgresql/data
      volumes:
      - name: postgres-storage
        persistentVolumeClaim:
          claimName: postgres-pvc

06-ingress.yaml

Tạo các Service (ClusterIP) cho frontend/backend và một Ingress để định tuyến traffic từ bên ngoài.

apiVersion: v1
kind: Service
metadata: {name: backend-service}
spec:
  type: ClusterIP
  selector: {app: backend}
  ports: [{port: 80, targetPort: 8000}]
---
apiVersion: v1
kind: Service
metadata: {name: frontend-service}
spec:
  type: ClusterIP
  selector: {app: frontend}
  ports: [{port: 80, targetPort: 80}]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  rules:
  - http:
      paths:
      - path: /api(/|$)(.*)
        pathType: Prefix
        backend:
          service: {name: backend-service, port: {number: 80}}
      - path: /(/|$)(.*)
        pathType: Prefix
        backend:
          service: {name: frontend-service, port: {number: 80}}

📈 Khám phá Nâng cao

Khi bạn đã nắm vững cơ bản, đây là các công cụ và khái niệm để vận hành hệ thống ở quy mô production.

Tự động Co giãn (Horizontal Pod Autoscaler - HPA)

Giống như siêu thị: Bạn đặt quy tắc (HPA): "Nếu khách chờ thanh toán (CPU utilization) ở bất kỳ quầy nào (Pod) vượt quá 70%, hãy *tự động mở thêm quầy mới* (tăng `replicas`), tối đa 10 quầy. Nếu khách giảm, hãy đóng bớt quầy."

Điều này giúp bạn tiết kiệm chi phí khi tải thấp và đảm bảo hiệu năng khi tải cao.

Mô phỏng HPA

Bấm nút bên dưới để mô phỏng lượng CPU tăng vọt và xem HPA phản ứng bằng cách tăng số lượng Pod (sau một khoảng trễ).

# (Chỉ làm 1 lần) Bật Metrics Server trên Minikube
minikube addons enable metrics-server

# Tạo HPA bằng CLI (scale từ 2-10 pod, mục tiêu CPU 50%)
kubectl autoscale deployment backend-api -n my-project --cpu-percent=50 --min=2 --max=10

# Xem HPA

CI/CD Pipeline (Workflow thực tế)

Tự động hóa quy trình từ `git push` đến deploy. Đây là workflow DevOps hoàn chỉnh:

1
Dev Git Push

Push code lên `main`

2
CI Server

(GitHub Actions, Jenkins...)

3
Build & Push Image

Build image Docker và push lên Registry (ECR, Docker Hub)

4
Deploy (GitOps)

ArgoCD/Jenkins cập nhật K8s cluster

Ví dụ: GitHub Actions Pipeline

File `.github/workflows/deploy.yml` này sẽ tự động build và deploy khi push lên `main`.

name: Build and Deploy to K8s
on:
  push:
    branches: [ main ]
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOKCER_USER }}
          password: ${{ secrets.DOKCER_PASS }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: my-company/my-backend:${{ github.sha }}
      
      - name: Set up Kubeconfig
        run: echo "${{ secrets.KUBE_CONFIG }}" > $HOME/.kube/config
      
      - name: Deploy to Kubernetes
        run: |
          kubectl set image deployment/backend-api \
            -n my-project \
            backend=my-company/my-backend:${{ github.sha }}

Quản lý Template (Helm & Kustomize)

Bạn có 7 file YAML. Làm sao để triển khai 1 môi trường `staging` giống hệt (chỉ khác DB pass, replicas)?

  • Helm (Giống như `dnf` hay `apt`): Đóng gói (package) toàn bộ 7 file YAML của bạn thành 1 `Chart`. Bạn có thể cài đặt cả một hệ thống phức tạp (như Prometheus) bằng 1 lệnh `helm install`. Tốt nhất để *phân phối* và *cài đặt* phần mềm của bên thứ 3.
  • Kustomize (Quản lý Overlay): Bạn giữ 1 bộ YAML *cơ sở* (base). Sau đó tạo các file *overlay* (ví dụ `staging`, `prod`) chỉ định *sự khác biệt* (ví dụ: `prod` sẽ patch `replicas: 10`). Tốt nhất để quản lý các môi trường (dev/staging/prod) cho *chính* ứng dụng của bạn.

Monitoring & Logging

Làm sao biết app đang lỗi, đang chậm?

  • Logging (EFK/Loki): `kubectl logs` chỉ xem được log của 1 Pod, Pod chết log mất. Giải pháp là dùng một tool (như `Fluentd`) tự động *gom* log từ *tất cả* các Pod và gửi về một nơi lưu trữ trung tâm (như `Elasticsearch` hoặc `Loki`).
  • Monitoring (Prometheus & Grafana):
    • Prometheus: "Kẻ săn lùng" metrics. Nó đi hỏi (scrape) tất cả các Pod/Node "CPU mày bao nhiêu?", "Bao nhiêu request/giây?"... và lưu lại.
    • Grafana: "Họa sĩ". Đọc dữ liệu từ Prometheus và vẽ thành các dashboard (biểu đồ) đẹp đẽ.
# Cài đặt dashboard, prometheus, grafana trên Minikube
minikube addons enable dashboard
minikube addons enable prometheus

Triển khai trên Cloud (AWS EKS)

Minikube/Kind là "xe tập lái". EKS/GKE/AKS là "xe đua F1".

Amazon EKS (Elastic Kubernetes Service) là dịch vụ K8s của AWS.

Khác biệt chính:

  • Control Plane (Bộ não): AWS quản lý *hoàn toàn*. Bạn không cần lo về etcd hay API Server.
  • Worker Nodes: Là các máy ảo `EC2` trong tài khoản của bạn.
  • Tích hợp Cloud (Điều tuyệt vời):
    • Bạn tạo Service `type: LoadBalancer` → EKS *tự động* tạo một `AWS Elastic Load Balancer` (ELB).
    • Bạn tạo `PVC` → EKS *tự động* tạo một ổ `AWS EBS`.
# Cài đặt 'eksctl' và 'aws-cli' (không nằm trong hướng dẫn này)

# Lệnh này tự động tạo TOÀN BỘ cluster production-ready trên AWS
eksctl create cluster \
  --name my-prod-cluster \
  --region us-east-1 \
  --node-type t3.medium \
  --nodes 3
